# shell体験 スタッフマニュアル

## 1. 体験の目的と所要時間

参加者が「黒い画面（ターミナル）は怖いもの」ではなく、「文字でコンピューターに指示を出すための身近な道具」だと実感してもらうことを目標とする。コマンドの暗記や用語の試験は行わない。

- 基本コース（1～3問）: 5～8分
- 発展コース（4～5問）: 追加で3～7分
- 対象: アルファベットと記号をキーボード入力できる人
- スタッフ配置: 体験PC 1～2台につき1人を目安とする

題材は「目撃記録から迷子のペンギンTuxを探し出す」というストーリー形式。画面左側に問題とヒント、右側に本物のbash（ターミナル）を表示する。参加者は右側でコマンドを実行し、見つけた答えを `answer 答え` の形式で送信する。ペイン（画面分割）のフォーカス移動などの操作は不要。

## 2. 当日までの準備

### 必要な環境

- LinuxまたはLinux VM
- Python 3.10以降
- bash
- tmux
- sudo権限を持たない体験専用ユーザー `trial`
- 日本語を表示できる端末と等幅フォント

VMを使用する場合は、ネットワーク、共有フォルダー、共有クリップボード、ドラッグ＆ドロップを無効化しておく。WSL2を使用する場合は、Windowsドライブの自動マウントおよびWindows interop機能も無効化する。体験環境内には個人ファイルや秘密情報を置かないこと。

### 開場前チェック

1. `trial` ユーザーでログインする。
2. 端末ウィンドウを最大化し、少し離れた位置からでも無理なく読める文字サイズに調整する。
3. `trial_tools/shells/new.py` を実行する。
4. 画面左側に問題、右側にプロンプト `trial$` が表示されることを確認する。
5. スタッフ自身で全5問を一通り解いてみて、後述の問題一覧表どおりに進められることを確認する。
6. `Ctrl+B` を押してキーを離したあと、`Shift+R`、`y` の順に入力してセッションを終了する。
7. 再度 `./new.py` を実行し、問題1へ正常に戻ることを確認する。

起動コマンド:

```sh
cd trial_tools/shells
./new.py
```

## 3. 参加者への案内

参加者が着席したら、まずは次のように案内する。

> 右側の黒い画面は、文字でコンピューターにお願い（指示）をする場所です。左側の問題を見ながら進めていきます。体験用の環境なので、入力を間違えても全く問題ありません。まずは `ls` と入力して、Enterキーを押してみてください。

あわせて、最初に伝えるポイントは以下の3点だけにとどめる。

- 画面に表示されている `trial$` は入力せず、その右側にコマンドを入力すること。
- ファイル名の入力途中で `Tab` キーを押すと、名前を自動補完できること。
- 答えが分かったら `answer 答え` と入力して送信すること。

最初からスタッフがコマンドを口頭で指示し続けるのではなく、参加者自身が左側の問題を読んでじっくり試行錯誤する時間を確保する。手が止まってしまった場合は、

1. 「左側には何を調べると書いてありますか？」
2. 「使えそうなファイルはどれでしょうか？」

の順に声をかけ、それでも難しそうな場合は画面のヒントや正解コマンドを案内する。

## 4. 問題と回答一覧

| 問題 | ねらい | 想定コマンド | 送信する答え |
| --- | --- | --- | --- |
| 1. ファイルを見つける | 一覧表示 | `ls` | `answer welcome.txt` |
| 2. ファイルを読む | 内容表示 | `cat welcome.txt` | `answer Tux` |
| 3. 必要な行を探す | 文字列検索 | `grep Tux members.txt` | `answer guide` |
| 4. 行番号も表示する | オプション | `grep -n Tux sightings.txt` | `answer PC Room` |
| 5. 組み合わせる | パイプと行数 | `grep Tux sightings.txt \| wc -l` | `answer 4` |

判定時、大文字・小文字や全角・半角、前後の空白などはシステム側で自動的に吸収される。また、想定コマンド以外の方法で答えにたどり着いた場合も正解として扱う。

3問目をクリアすると、基本コースの完了画面が表示される。混雑時や参加者が疲れている様子なら `answer finish` で終了し、まだ余裕や興味がありそうなら `answer next` を入力して発展コースへ進めてもらう。

## 5. サポートの基準

### 入力に慣れていない参加者

- 一度に伝える操作は1つだけにとどめる。
- ファイル名はTabキーによる補完を使ってもらう。
- 記号 `|`（パイプ）の入力に戸惑っている場合は、キーボード上の位置を指し示して教えてよい。
- スタッフが代わりに入力する場合でも、Enterを押して実行する前に、どんなコマンドなのかを参加者へ説明する。

### 早く終わった参加者

時間や興味に応じて、以下の自由課題から1つだけ案内してみる。

- `grep` と `grep -n` の出力の違いを見比べる。
- `grep Mochi sightings.txt | wc -l` で別の名前を数えてみる。
- 上矢印キー（`↑`）で直前のコマンド履歴を呼び出し、一部分だけ書き換えて実行してみる。

教材ディレクトリ外を探索させる操作や、ソフトウェアのインストール、ネットワークを利用するような課題は案内しないこと。

### 説明の締め

> `cat` や `grep`、`wc` は、それぞれ単機能の小さな道具です。最後の問題では、それらを `|`（パイプ）でつなぎ合わせました。Linuxのターミナルでは、このように小さな道具を組み合わせることで、自分が必要な処理を自由自在に作ることができます。

## 6. 次の参加者への初期化

1. 体験が完了したことを確認する。
2. `Ctrl+B` を押してキーを離す。
3. `Shift+R` を押す。
4. 確認メッセージが表示されたら `y` を押す。
5. ターミナルで `./new.py` を実行する。
6. 右側のペインがアクティブ（選択状態）になっており、左側に問題1が表示されていることを確認する。

セッションごとに新しい作業ディレクトリが自動作成されるため、前の参加者が行った変更が次の回へ引き継がれる心配はない。過去の作業ディレクトリは閉場後に管理者が一括削除するため、スタッフ自身の当日判断で上位階層や関係ないディレクトリを削除（`rm`）しないこと。

## 7. トラブル対応

### コマンドが動かない

- `command not found`: スペルミスや全角文字の混入がないか、半角英数字で正しく入力されているか確認する。
- `No such file or directory`: ファイル名が合っているかを `ls` で確認し、Tab補完を使うよう案内する。
- 画面の応答が止まった: `Ctrl+C` を1回押して処理を中断する。
- 文字が画面に大量に流れてしまった: `Ctrl+C` で出力を止め、`clear` を実行して画面を整える。
- `answer` に答えを付け忘れた: コマンドの使用例が表示されるため、引数に答えを付けてもう一度入力し直す。

### 左側の問題が進まない

1. 右側に「左側へ答えを送りました」とメッセージが出たか確認する。
2. 回答一覧と照合し、答えが合っているか確認する。
3. 数秒待っても画面が変わらなければ、そのセッションを終了して `./new.py` で新しく起動し直す。

### paneやshellを閉じてしまった

その回を終了し、新しいセッションを起動する。「体験用の環境なので、すぐに最初からやり直せますよ」と安心させ、決して参加者の操作ミスを責めないこと。

### `new.py` が起動しない

- `tmuxが見つかりません`: tmuxのインストールを担当スタッフへ依頼する。
- `教材ファイルがありません`: `new.py` だけを別の場所へ移動していないか確認する。
- tmux関連のエラー: `tmux list-sessions` の実行結果と画面のエラー表示をコアスタッフへ伝える。

原因調査に時間を取られすぎないようにし、速やかに予備PCへ案内する。参加者の前で `sudo` を使った復旧作業や環境設定の変更は行わないこと。

## 8. スタッフが覚える操作

| 操作 | キーまたはコマンド |
| --- | --- |
| 体験を起動 | `./new.py` |
| 実行中のコマンドを止める | `Ctrl+C` |
| 画面を整理する | `clear` |
| 体験を終了 | `Ctrl+B` → `Shift+R` → `y` |
| tmuxセッション一覧 | `tmux list-sessions` |

参加者の入力内容を細かく採点する必要はない。正解への最短ルートを教えることよりも、「自分の手でファイルを調べ、必要な情報を見つけ出せた」という発見の体験を優先する。
